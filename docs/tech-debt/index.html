    Technical Debt¶

    Each entry has a unique ID referenced in the source code via // TECHDEBT(TD-XXX): comments. Run grep -r 'TECHDEBT' crates/ to find all markers.

    TD-023 Offline migrate-db has no crash-safe checkpoint The offline arca migrate-db CLI copies every table to the destination in a single process with no checkpoint; a crash or SIGKILL mid-run leaves the destination partially written and the operator must drop it before retrying. (The migrate-topology CLI is not affected: its operations are idempotent/in-place — tombstone purge is safely re-runnable, VACUUM is a no-op on restart.)     TD-025 Cluster conditional writes (CAS) Cluster-wide conditional-write atomicity is not provided: If-Match / If-None-Match / x-amz-if-match-* preconditions are evaluated authoritatively only against the serving node's own state (put_object_if/delete_object_if/delete_object_version_if commit locally, then fan out — there is no per-key authoritative node to arbitrate across peers). Concurrent conditional writes for the same key landing on two different nodes at once can both pass their own local CAS and both be accepted (200 OK); the row then converges by last-writer-wins, the same as any other conflicting write. Single-node CAS (the common case, and the whole point of the conditional-write-atomicity fix) is unaffected — see crates/arca-storage/src/{sqlite,pg}/metadata.rs. Mitigated operationally by pinning a given key's conditional-write traffic to one node (a sticky/session-aware load balancer — see documentation/docs/guide/ha.md). Owner-node forwarding for conditional writes: the node that receives a conditional PUT/DELETE for a key it doesn't own forwards it to that key's designated owner node instead of committing locally, giving cluster mode the same per-key authoritative arbitration single-node CAS already has. None (cluster CAS boundary is pinned by tests/integration/test_cluster.py::test_conditional_put_is_per_node_not_cluster_wide; single-node CAS is fully covered by tests/integration/test_conditional_writes.py) crates/arca-server/src/cluster/cluster_meta.rs (put_object_if, delete_object_if, delete_object_version_if)
    TD-014 recover / fsck composite blobs Composite blobs (the result of the optimised CompleteMultipartUpload) live as a sidecar that lists the part blob ids — no on-disk file exists at the composite's blob path. recover::process_sidecar rejects them as "orphaned sidecar (blob file missing)"; the caller prints a WARNING and skips the sidecar, so every multipart object is silently dropped from the rebuilt database. Worse, the retained part blobs carry ordinary sidecars whose key is {key}#{upload_id}#{part_number} (handlers/multipart.rs), so recover re-creates each part as a bogus object under that key. Parts produced by UploadPartCopy get a sidecar only when encrypted, so a plain copied part is invisible to recover and forces FsBlobStore::concat off the composite fast path (full byte copy). fsck reports the composite sidecar as an orphaned_sidecars entry (the parts themselves are not orphaned because they each carry their own sidecar). Both tools therefore misbehave on any data directory that has experienced multipart uploads after the composite-concat optimisation. Runtime S3 reads/writes are unaffected — the request path fully handles composites. (1) recover: when a sidecar has composite: Some(parts), skip the blob-existence check, walk the part list, and verify each referenced part blob exists. Insert one ObjectRecord per composite that points at the composite blob_id (the part records are not surfaced to the metadata DB — they are a storage-layer detail). (2) fsck: treat composite sidecars as valid (no blob file expected); cross-check each referenced part exists; report a new dangling_part category when a composite references a missing part. Add unit tests for both tools using fixtures that mix composite and ordinary blobs. None at the runtime level; recovery / fsck workflows on data with composites currently fail crates/arca-server/src/recover.rs:206, crates/arca-server/src/fsck.rs (orphaned_sidecars collection, around line 112)
    TD-032 arca recover rebuilds a wrong database Besides TD-014: (1) entries are sorted by last_modified descending and buckets are re-created unversioned, so each put_object overwrites the previous one and the oldest version of every key wins, while the code comment says the newest is inserted last; (2) only buckets, objects and credentials are restored — users, teams, grants, every bucket_config (versioning, encryption, lifecycle, lock, policy, notifications, replication), bucket/object tags, retention and legal hold are lost, and owner is forced to root; (3) compressed objects fail checksum verification (the ETag is the plaintext MD5, recover hashes the on-disk bytes) and are skipped unless --skip-verify; (4) it always opens a SQLite store, so on a PostgreSQL deployment it writes an unused SQLite file; (5) PutObject, CopyObject and CompleteMultipartUpload write the sidecar with version_id: None before the metadata commit assigns the version, so sidecars never carry it and a rebuild cannot restore version ids. operations/recovery.md documents none of this and claims the opposite for (1). Insert newest-last (and re-create versioned buckets as versioned, keeping version_id), verify compressed objects against the decompressed stream, support the configured backend, and document precisely what a sidecar rebuild can and cannot restore. Unit tests with multi-version, compressed and composite fixtures. None (no integration coverage of recover on such data) crates/arca-server/src/recover.rs, documentation/docs/operations/recovery.md

    TD-038 No fsync on the write path Blob writes flush() and rename() but never sync_all() the file or its directory, and write_sidecar uses a plain, non-atomic fs::write.     TD-040 Cluster maintenance jobs can stall on a non-leader node Maintenance jobs are stored in each node's local MaintenanceStore (not cluster-wrapped, not part of ControlSnapshot), while only the worker-leader (lowest eligible node_id, decision H5) runs the maintenance worker. A job created through the load balancer on any other node is never picked up until that node happens to become leader; the API accepts it and it stays pending. guide/maintenance.md and guide/console.md do not mention this. Route job creation (and pause/cancel) to the worker-leader over /cluster/v1/*, or replicate the jobs table as a control-plane family and let the leader claim jobs. Until then, document that jobs must be created on the leader node. None crates/arca-server/src/maintenance.rs (spawn_maintenance_worker), crates/arca-proto/src/handlers/maintenance.rs, crates/arca-server/src/main.rs (store wiring)
    TD-041 Blob ids received from cluster peers are not validated parse_blob_id (UUID check) guards only the /cluster/v1/blob/{blob_id} path parameter.
